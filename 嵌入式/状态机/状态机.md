# 状态机笔记（嵌入式视角）

## 一、状态机的含义

**有限状态机**（Finite State Machine, FSM）是一种为"响应式系统"建模的数学模型：系统在任何时刻恰好处于**有限个状态之一**；当**事件**（输入、中断、定时器到期、消息……）发生时，系统根据"当前状态 + 事件"决定**转移**到哪个新状态，并在进入/离开状态或发生转移时执行**动作**。

五个基本要素：

- 状态（State）：系统在某一时刻的抽象处境，是对"过去历史"的浓缩。
- 事件（Event）：触发状态变化的刺激。
- 转移（Transition）："当前状态 + 事件 → 新状态"的规则，可带守卫条件（Guard）。
- 动作（Action）：转移时、进入状态时（entry）、离开状态时（exit）执行的行为。
- 初始状态与终止状态。

**状态的本质**（Miro Samek 的经典表述）：状态不是代码的位置，而是"过去事件序列的等价类"——凡是产生相同未来行为的过去，都属于同一个状态。理解了这一点，才能正确地划分状态：划分标准不是"程序走到哪一步"，而是"哪些历史对未来行为的影响相同"。

**状态机 vs 流程图**：流程图描述"下一步做什么"（顺序变换范式），状态机描述"在什么情况下对发生的事情如何反应"（事件驱动范式）。嵌入式系统本质上是响应外部世界的，因此用状态机建模更贴切。

## 二、目的（为什么要用状态机）

1. **把复杂行为显式化**：系统"在什么状态下收到什么事件该干什么"一目了然，避免散落的 if/else 和标志位。
2. **消灭"标志位爆炸"**：用多个布尔标志的组合隐式表达状态时，状态空间是 2ⁿ，其中绝大多数组合是无意义或非法组合；状态机把合法状态收敛到有限、有名字的集合。
3. **可读性与可维护性**：状态图本身就是文档；需求变更通常是"加一个状态"或"加一条转移"，影响面局部。
4. **可测试性**：状态和转移可以枚举，能自动生成测试用例（状态覆盖、转移覆盖、关键路径覆盖）。
5. **可形式化验证**：FSM 有严格数学定义，可以用模型检查工具（NuSMV、TLA+ 等）发现死锁、不可达状态、活锁。
6. **资源确定性**：经典实现不需要动态内存、不依赖递归，状态数静态可知——这正是嵌入式环境需要的。
7. **贴合嵌入式本质**：硬件和协议本身就是状态机（电源管理、USB、蓝牙、充电协议、总线时序），用状态机建模等于用问题自己的语言描述问题。

## 三、类型

### 按输出分类

- **Moore 机**：输出只由当前状态决定。输出稳定（适合状态指示类信号），但通常需要更多状态。
- **Mealy 机**：输出由"状态 + 输入"共同决定（动作写在转移上）。状态少、反应快，但输出时序上可能产生毛刺。工程实践中绝大多数实现是 Mealy 风格。

### 按结构分类

- **有限状态机（FSM）**：扁平的一层状态，switch-case 就能实现。
- **层次状态机（HSM）**：状态可以嵌套，子状态**继承**父状态的所有转移。思想源自 David Harel 1987 年的 **Statechart** 形式化。带来的特性：
  - 嵌套与默认转移：进入复合状态时先自动进入其默认子状态；
  - 进入/退出动作：沿层次链逐级执行 entry/exit；
  - 历史伪状态（H）：重新进入复合状态时恢复到上次离开时的子状态；
  - 并行区域（正交区域）：多个独立维度同时活跃（如"电源域"与"通信域"并行）；
  - 解决**状态爆炸**：n 个正交维度若扁平化会变成状态乘积爆炸，层次化只需分别描述 n 套。
- **并发状态机**：多台 FSM 并行运行。嵌入式里通常是多个**活动对象（Active Object）**各跑一台状态机，彼此靠消息/事件通信，而不是共享变量。

### 其他常见划分

- 确定性 / 非确定性：同一状态收到同一事件是否只有一条转移。实现时必须消除歧义（给转移定优先级），否则行为不可复现。
- 面向对象**状态模式**（GoF《设计模式》）：把每个状态封装成对象/类，对象行为随内部状态改变而改变。嵌入式 C 中常用函数指针表模拟。

## 四、实现范式（以 C 语言为主）

### 1. switch-case 法（状态内分发事件）

```c
switch (state) {
case IDLE:
    if (ev == EV_START) { start_motor(); state = RUNNING; }
    break;
case RUNNING:
    if (ev == EV_STOP)  { stop_motor();  state = IDLE; }
    if (ev == EV_FAULT) { alarm();       state = FAULT; }
    break;
}
```

优点：直观、零额外开销、易调试。缺点：状态和事件一多就分支爆炸，逻辑散落在各处。

### 2. 表驱动法（状态 × 事件 → {下一状态, 动作}）

```c
typedef struct { int next; void (*action)(void); } trans_t;
trans_t table[N_STATES][N_EVENTS] = {
    [IDLE][EV_START]    = { RUNNING, start_motor },
    [RUNNING][EV_STOP]  = { IDLE,    stop_motor  },
    [RUNNING][EV_FAULT] = { FAULT,   alarm       },
};
```

优点：全部转移关系集中在一张表里；查表本质是一次二维数组寻址，平均效率高于长 switch；扩展 = 加行加列。缺点：动作函数签名难以统一（需要变参或统一上下文结构体），调试不如 switch 直观。

### 3. 函数指针法（状态即函数，返回下一状态）

```c
state_fn_t state = st_idle;
state = state(ev);   /* 每个状态函数内部分发事件，返回下一状态函数 */
```

优点：每个状态的逻辑聚合成独立函数，便于复用与分层。缺点：可读性对新手不友好，上下文传参需仔细设计。

### 4. 状态表 + 动作指针混合（生产项目常用）

状态用枚举表示，转移表里存"下一状态 + 入口/出口动作函数指针"，配合 entry/exit 钩子使用，兼顾表驱动的高效和 switch 的可读。

### 5. 事件驱动框架 + 层次状态机（QP 路线）

把状态机封装为**活动对象**：每个对象拥有私有事件队列和（逻辑上的）执行线程，事件循环里调用层次状态机的分发函数。代表实现：[Quantum Leaps QP/C](https://www.state-machine.com/qpc)、[Zephyr SMF](https://docs.zephyrproject.org/latest/services/device_mgmt/smf.html)。适合逻辑复杂、并发事件多的产品级项目。

### 选型经验

- 状态少而密：用 switch-case，最快最直白；
- 状态多而疏（转移矩阵稀疏）：用表驱动；
- 状态逻辑需要复用或分层：用函数指针或 HSM 框架；
- 产品级、多任务事件并发：用 QP 类框架；
- 无论哪种：**先画状态图，后写代码**。

## 五、设计实践要点

1. 先定义**完整的事件清单**，再定义状态——事件集稳定后，状态机才稳定。
2. 为每个状态显式处理**每个事件**（哪怕动作是"忽略"），转移矩阵不留空洞。
3. 进入/退出动作放在 entry/exit 里，不要混进转移动作——层次化、调试、复用都会受益。
4. 时间用**事件**建模：定时器到期是 EV_TIMEOUT，绝不在状态内部忙等 delay。
5. 警惕**隐式状态**：两个布尔标志 = 最多 4 个隐式状态，三四个标志组合起来就失控；凡是用"多个标志判断下一步"的地方，都该考虑提炼成显式状态。
6. 画状态图工具：QM（免费）、PlantUML、draw.io；复杂项目可用模型检查做一次死锁/不可达检查。
7. 与 RTOS 的关系：把每个并发对象做成一个任务，**任务 = 活动对象，消息队列 = 事件队列**，状态机只处理自己的队列，避免共享变量竞争。
